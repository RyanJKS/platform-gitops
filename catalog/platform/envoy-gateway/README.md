# Envoy Gateway

Envoy Gateway watches Gateway API resources. Controller creates Envoy proxy
Deployments and Services. Envoy proxies handle application traffic.

Catalog installs controller and extension CRDs through official OCI charts,
pinned to `v1.9.2`. Shared [Gateway API Application](../gateway-api/README.md)
owns `gateway.networking.k8s.io` CRDs separately. Controller chart disables
bundled CRDs; extension chart disables Gateway API CRDs. Keep one CRD owner.

Separate from Cilium's Envoy integration. No Cilium networking changes.
Catalog creates no GatewayClass instance, Gateway, routes, DNS records, or
application TLS certificates. Chart generates internal controller certificates.

## Files

- [application.yaml](application.yaml): controller and extension CRD Helm sources; values Git source.
- [values.yaml](values.yaml): shared controller settings.
- [repository.yaml](repository.yaml): registers `docker.io/envoyproxy` as OCI Helm repository in Argo CD.
- [envoyproxy.yaml](envoyproxy.yaml): shared settings for Envoy proxies serving application traffic.
- [samples/gatewayclass.yaml](samples/gatewayclass.yaml): GatewayClass example referencing shared EnvoyProxy. Not selected automatically.
- [kustomization.yaml](kustomization.yaml): selects Application, repository Secret, and EnvoyProxy.

## Shared EnvoyProxy

`EnvoyProxy` stores proxy deployment settings. It does not install controller.
Controller reads these settings when reconciling Gateways.

Catalog default:

- Name: `gateway-configuration`.
- Namespace: `envoy-gateway-system`.
- Provider: `Kubernetes`.
- Proxy replicas: `2` per generated Deployment.
- Rolling updates: at most `1` extra Pod; `0` unavailable Pods.
- Proxy Service type: `LoadBalancer`.
- Proxy Service name: `envoy-gateway-default`. Multiple Gateways need distinct Service names or autogenerated names.
- External traffic policy: `Local`, preserving client source IPs.
- Proxy log level: `warn`.
- Access logs: structured JSON to proxy container stdout.

GatewayClass selects shared EnvoyProxy through `spec.parametersRef`:

```yaml
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
  parametersRef:
    group: gateway.envoyproxy.io
    kind: EnvoyProxy
    name: gateway-configuration
    namespace: envoy-gateway-system
```

GatewayClass is cluster-scoped. EnvoyProxy is namespaced; reference must include
correct namespace. Keep reference aligned when changing EnvoyProxy name or
namespace. Defaults apply to Gateways using that GatewayClass.

Gateways select class through `spec.gatewayClassName: envoy-gateway`.
HTTPRoutes select Gateway through `parentRefs`. Gateway listeners define ports,
hostnames, and TLS. EnvoyProxy alone creates no proxy Deployment or Service.

## Customization scope

EnvoyProxy controls how controller builds and runs traffic proxies. Capabilities
extend beyond replicas. Catalog file exposes common settings and commented
examples; it does not enable every feature.

Under `spec.provider.kubernetes`:

- `envoyDeployment.replicas`: fixed proxy count. Separate from controller replicas in Helm values.
- `envoyDeployment.strategy`: rolling update limits. Current settings need capacity for one extra Pod per updating Deployment.
- `envoyDeployment.container.resources`: CPU and memory requests and limits. Commented values are examples; size for traffic.
- `envoyDeployment.pod`: node selectors, affinity, tolerations, topology spread, labels, annotations, and security settings.
- `envoyHpa`: proxy autoscaling, replica bounds, metrics, and scaling behavior. HPA overrides fixed replicas. CPU utilization needs CPU requests and working metrics API.
- `envoyPDB`: disruption budget for voluntary disruptions. Example `minAvailable: 1` needs at least two replicas to allow drains.
- `envoyService`: Service type, external traffic policy, annotations, and load balancer settings. Keep Azure annotations in cluster overlays.

Other `spec` settings include proxy log levels (`logging`), worker threads
(`concurrency`), access logs, Prometheus metrics, and tracing (`telemetry`).
Prometheus example configures endpoint; configure scraping separately.

Referenced EnvoyProxy supplies defaults to Gateways using that GatewayClass.
Changing shared settings can update several proxy Deployments. Without
`mergeGateways`, replicas apply per Gateway Deployment, not across whole class.
Keep `mergeGateways` unset unless shared proxy infrastructure is intended.

Patch values in cluster `envoy-gateway/kustomization.yaml`, using target group
`gateway.envoyproxy.io`, version `v1alpha1`, kind `EnvoyProxy`, name
`gateway-configuration`, and namespace `envoy-gateway-system`. For example, replace
`/spec/provider/kubernetes/envoyDeployment/replicas` with `3` for three proxies per
Deployment. Keep reusable defaults in catalog.

`Local` sends external traffic only to nodes with local ready proxy Pods.
Spread replicas across nodes for availability. EnvoyProxy configures proxy
infrastructure; routes, certificates, authentication, and traffic policies still
use Gateway API resources and relevant Envoy Gateway policy resources.
Supported fields depend on pinned controller and CRD version.

## Access logs, formats, and sinks

`spec.telemetry.accessLog` controls request access logs. Separate from
`spec.logging.level`, which controls proxy diagnostic logs. Without explicit
access-log settings, Envoy Gateway already sends default access logs to stdout;
catalog now selects structured JSON fields explicitly.

- `disable: false`: keep access logging enabled. Set `true` to disable it.
- `settings[].format`: choose `JSON` with `json`, or `Text` with `text`. Use matching field only.
- JSON keys define output fields; values use Envoy access-log operators. Examples: `%RESPONSE_CODE%`, `%DURATION%`, `%UPSTREAM_HOST%`.
- Current fields include request method/path, response code/flags, duration, byte counts, upstream host, client address, and request ID.
- `settings[].sinks`: choose destinations. One setting can send logs to several sinks.
- `File` with `/dev/stdout`: writes proxy container logs. Log collection and retention require separate setup.
- `OpenTelemetry`: exports through OTLP gRPC to collector. Commented example uses Service `otel-collector` on port `4317` in EnvoyProxy namespace. Deploy collector before enabling.
- For collector in another namespace, set backend reference namespace and configure required ReferenceGrant. Keep collector deployment settings in cluster overlay.
- `ALS`: sends Envoy gRPC Access Log Service records to compatible receiver; `format` is ignored for this sink.

Current setting omits `type`, retaining default coverage: routes, plus listener
requests without matching route. Explicit `type: Route`, `Listener`, or
`Upstream` changes emitting component. Additional settings may produce multiple
records for one request; select scope deliberately.

For plain text, replace current `format` block with:

```yaml
format:
  type: Text
  text: "[%START_TIME%] %REQ(:METHOD)% %REQ(:PATH)% %RESPONSE_CODE% %DURATION%ms\n"
```

Keep current `sinks` block. Do not retain `json` alongside `type: Text`.
Prometheus settings remain a separate `telemetry.metrics` block; enabling
metrics does not configure log export or scraping.

Inspect proxy container logs after sync:

```sh
kubectl -n envoy-gateway-system get pods
PROXY_POD=REPLACE_WITH_PROXY_POD_NAME
kubectl -n envoy-gateway-system logs "$PROXY_POD" -c envoy --tail=20
```

Choose proxy Pod, not Envoy Gateway controller Pod. Rendering checks structure;
runtime logs confirm operator expansion and collector delivery.

## ClientTrafficPolicy

ClientTrafficPolicy controls connections from clients to Envoy. EnvoyProxy
controls proxy infrastructure. BackendTrafficPolicy controls traffic from Envoy
to backend Services. These resources solve different problems.

[AKS Envoy learning example](../../../clusters/azure/DEV-JKS/dev/uks/sandbox/aks-envoy/apps/platform/gateways/clienttrafficpolicy.yaml)
lives in cluster `gateways/`, selected by its Kustomization. Policy stays
cluster-owned because target Gateway and listener names belong to cluster.
Catalog controller installs ClientTrafficPolicy CRD with other extension CRDs.

Example targets Gateway `platform-gateway` in namespace `argocd`:

- `targetRefs`: select Gateway in same namespace. Omit `sectionName` to cover all listeners; set `https` to select HTTPS listener only.
- `timeout.http.idleTimeout: 3600s`: close connection after one hour without active requests.
- `timeout.http.streamIdleTimeout: 300s`: close stream after five minutes without traffic in either direction. Account for quiet watches and streaming clients when changing it.
- `tcpKeepalive`: enable TCP probes after `60s` idle, repeat every `10s`, allow `3` unanswered probes. Socket liveness differs from HTTP timeouts.
- `http2.maxConcurrentStreams: 100`: limit concurrent streams per HTTP/2 connection. Not a global request rate limit.

HTTP idle values and stream limit make existing defaults explicit. TCP
keepalive is enabled by this example; it is disabled when unspecified.
Settings are active when cluster root syncs. Commented examples add request
header deadline, TLS protocol bounds, and trusted-proxy client IP detection.

Before enabling TLS example, select HTTPS listener through `sectionName: https`.
Gateway listener still owns certificate references and TLS termination.
Configure `xForwardedFor.numTrustedHops` only for known trusted HTTP proxies.
Current Azure LoadBalancer path does not need one trusted HTTP hop. Trusting
client-supplied forwarded headers permits IP spoofing.

ClientTrafficPolicy also supports client certificate validation, HTTP/3,
connection limits, and header handling. Fields depend on pinned CRD version.
Use Gateway/listener targeting here; HTTPRoute targeting is not supported by
this policy. Avoid overlapping policies while learning; inspect policy status
for attachment errors and conflicts.

Parent AppProject must allow `gateway.envoyproxy.io/ClientTrafficPolicy` when
namespace resources are restricted. Example uses root wave `0` and
`SkipDryRunOnMissingResource=true` while extension CRD is missing.

After syncing, inspect attachment status and test existing routes:

```sh
kubectl -n argocd get clienttrafficpolicy platform-gateway -o yaml
```

Check `status.ancestors[].conditions` for `Accepted=True` and any other
reported errors. Rendering alone does not prove controller acceptance.

## Provider configuration

Keep reusable defaults in catalog. Patch EnvoyProxy in cluster overlay for
cloud load balancer annotations, proxy Service settings, or proxy scheduling.
Keep cloud identities, network ranges, DNS settings, and TLS Secrets in cluster
files. Kubernetes cloud provider or local LoadBalancer implementation supplies
proxy's external address.

Controller settings and proxy settings differ:

- `values.yaml`: controller Deployment and internal `ClusterIP` Service.
- `envoyproxy.yaml`: Envoy proxy Deployments and Services created for Gateways.

Controller Helm Service settings do not configure proxy Services. Controller
overrides belong under Application `spec.sources[0].helm.valuesObject`; retain
`crds.enabled: false`. Keep both chart versions aligned during upgrades.
See upstream [EnvoyProxy configuration](https://gateway.envoyproxy.io/docs/api/extension_types/#envoyproxy).

## Select in Argo CD

1. Import catalog directory into cluster Kustomization.
2. Ensure compatible Gateway API CRDs exist. Select `catalog/platform/gateway-api` only when Argo CD owns CRDs.
3. Patch Application project, destination, and values Git revision (`spec.sources[2].targetRevision`) as needed. Revision must contain selected catalog files.
4. Select cluster-owned GatewayClass from sample. Add cluster Gateways, HTTPRoutes, and certificates.

Repository Secret uses namespace `argocd`; patch namespace if Argo CD runs
elsewhere. Application Helm `repoURL` omits `oci://` prefix.

Root sync waves:

- `-5`: OCI repository registration.
- `-4`: shared Gateway API Application.
- `-3`: Envoy Gateway Application; creates `envoy-gateway-system` and installs extension CRDs.
- `0`: EnvoyProxy and cluster routing resources.

Parent Application health checks must wait for controller child to become
synced and healthy before wave `0`. Existing children reconcile independently.
EnvoyProxy uses `SkipDryRunOnMissingResource=true` while extension CRD is missing.
Application enables automatic sync, self-healing, and server-side apply;
automatic pruning stays disabled.

AppProjects must allow chart and values repositories, destination namespace,
cluster-scoped CRDs, RBAC, and chart's MutatingWebhookConfiguration. Parent
AppProject must allow `gateway.envoyproxy.io/EnvoyProxy` in
`envoy-gateway-system` when namespace resources are restricted.

Shared Gateway API catalog selects seven standard CRDs. Before using TCPRoute,
UDPRoute, ListenerSet, or other APIs outside selection, extend shared CRD
selection and review compatibility. Do not enable bundled Gateway API CRDs to
add APIs. Review existing ownership before migration.

## Validation

Render from repository root:

```sh
kubectl kustomize catalog/platform/envoy-gateway
```

With intended cluster selected, verify Application reports `Synced` and
`Healthy`, then check controller and shared settings:

```sh
kubectl -n argocd get application envoy-gateway
kubectl -n envoy-gateway-system rollout status deployment/envoy-gateway --timeout=600s
kubectl get crd envoyproxies.gateway.envoyproxy.io
kubectl -n envoy-gateway-system get envoyproxy gateway-configuration -o yaml
kubectl get gatewayclass envoy-gateway -o yaml
```

After selecting routing resources, check GatewayClass `Accepted`, Gateway
`Accepted`/`Programmed`, and HTTPRoute `Accepted`/`ResolvedRefs` conditions.
Confirm proxy Service has address. Test DNS, HTTP, and HTTPS. Rendering does
not prove controller readiness or cloud load balancer access.

Review upstream [installation guide](https://gateway.envoyproxy.io/docs/install/install-helm/)
and [release notes](https://gateway.envoyproxy.io/news/releases/notes/v1.9.2/)
before changing chart pins or CRD ownership.
